Overview – Final System Design
────────────────────────────────────────────────────────────────

This document describes a unified event‑logging system that serves as 
the backbone for user journey analytics, debugging, and sales 
optimization. Every meaningful user interaction—from launching the 
app to adding an item to the cart, completing a quiz, or encountering 
an error—is captured as a structured event. All events flow through a 
single, monolithic `EventLogger` class, which enforces data quality, 
embeds client‑side logs, and persists everything into a single SQL 
table. The result is a complete, time‑ordered stream of data that 
powers an elegant admin dashboard, AI‑driven insights, and friction‑
free debugging.

The system is built with three core principles:
• **Ethical by design** – We collect only minimal, permission‑free 
  data: basic device info, IP address (hashed), and app‑specific 
  interactions. No unnecessary tracking.
• **Simplicity through unity** – One class, one table, one consistent 
  API. Adding new event types does not require code changes; schemas 
  are stored in a database table and the system validates against them.
• **Debuggability first** – Every event automatically includes the 
  last 10 client‑side logs (screen transitions, network calls, errors) 
  so that engineers can reconstruct the exact state leading up to any 
  event.

The system comprises two main components:
1. A server‑side `EventLogger` class (this document) that receives, 
   validates, enriches, and stores events.
2. A client‑side logging utility (for Android/iOS) that automatically 
   collects the last 10 client logs and attaches them to every server 
   payload.

All data is stored in a single SQL table (`events`), making queries 
for dashboards, funnel analysis, and AI models straightforward and 
performant.


DESIGN PHILOSOPHY
────────────────────────────────────────────────────────────────

The system rejects the notion of multiple classes for users, sessions, 
milestones, carts, etc. Instead, it treats all of these as different 
“event types” within a unified stream. This monolithic approach yields 
several advantages:
• **Single source of truth** – All events are in one table, eliminating 
  joins and complex aggregations.
• **Flexible schema evolution** – New event types are defined by adding 
  a row to the `event_schemas` table; the server validates incoming 
  events against these schemas.
• **Complete user context** – Because every event carries a user object 
  and an auth token, there is never an orphaned event.
• **Client logs are part of the event** – Debugging no longer requires 
  separate log aggregation tools; the exact client state is stored 
  alongside the server event.
• **Built for AI** – The unified event stream is the perfect training 
  dataset for LLMs and predictive models, enabling endless sales 
  optimization strategies.


THE CORE CLASS: EventLogger
────────────────────────────────────────────────────────────────

The `EventLogger` is a singleton class instantiated once per server 
instance. It exposes three public methods: `newEvent`, `batchEvents`, 
and `getEvents`. All internal logic (validation, enrichment, queuing, 
persistence) is kept private, ensuring a clean API.

The class relies on a database table called `event_schemas` that stores 
the validation rules for each event type. This table is populated once 
during initial setup and updated only when new event types are 
introduced. The structure of `event_schemas` is minimal:
- `event_name` (string, primary key)
- `schema_json` (JSON schema defining the allowed fields in `details`)
- `options_json` (metadata: whether the event is a milestone, whether 
  it should be tracked in funnels, retention policy, etc.)

When the server starts, it does not need to preload schemas; the 
`EventLogger` simply queries the `event_schemas` table on‑demand and 
caches the schemas in memory for performance.


KEY METHODS (Public API)
────────────────────────────────────────────────────────────────

1. EventLogger.newEvent(eventSpec)
   ────────────────────────────────────────────────────────────────
   **Purpose**: Record a single event with full context.

   **Signature**:
     newEvent({
       authToken: string | object,   // JWT or session token
       user: {
         id?: string,
         anonymousId?: string,
         name?: string,
         email?: string               // only if consented
       },
       dateTime: string,              // "DD-MM-YY_HH:MM:SS" client time
       eventData: {
         name: string,                // e.g. "add-to-cart", "screen-view"
         details: object,             // polymorphic; must match schema
         clientLogs?: object          // appended by client; see below
       }
     })

   **Behaviour** (step‑by‑step):
     1. **Authentication & User Context** – The `authToken` is 
        validated (if present). The user object is merged with the 
        server’s known user data (e.g., fetching the user ID from the 
        token if not provided). An anonymous ID is generated if 
        neither `id` nor `anonymousId` is supplied.
     2. **Enrichment** – The event is enriched with:
        - `serverTimestamp`: ISO timestamp from the server’s clock.
        - `eventId`: a unique UUID or monotonically increasing ID.
        - `hashedIp`: SHA‑256 of the client’s IP address (derived from 
          the request, not the payload). This allows geo‑aggregation 
          without storing raw IP.
        - `deviceInfo`: pulled from the `user` object or request 
          headers (OS version, device model, etc.).
     3. **Schema Validation** – The method queries the `event_schemas` 
        table (or uses an in‑memory cache) to retrieve the JSON schema 
        for the given `eventData.name`. It validates the `details` 
        object against that schema. If the event name is not 
        registered, the event is rejected with a clear error (unless 
        configured to log a warning and store anyway).
     4. **Client Logs Handling** – The `clientLogs` object is merged 
        into the event record. The client is expected to send the last 
        10 client‑side logs as a structured object (see the client 
        section below). This field is not validated against a schema; 
        it is stored as a JSON blob for debugging.
     5. **Queue & Persist** – The enriched event is placed into an 
        in‑memory queue. A separate worker process (or background 
        thread) flushes the queue to the `events` SQL table in batches 
        of 100 or every 2 seconds, whichever comes first. This 
        decouples the API call from the database write, ensuring low 
        latency for the client.
     6. **Error Handling** – If validation fails, the method throws a 
        `ValidationError` with details. If persistence fails (e.g., 
        database outage), the event is written to a fallback file‑based 
        log for later replay.

   **Strengths & Innovative Nature**:
     • **Polymorphic yet strict**: The same method handles all event 
       types, but each type is validated against a defined schema. 
       This prevents data corruption while keeping the API surface 
       tiny.
     • **Client logs are automatic**: By including `clientLogs` in 
       every event, we turn each server‑side record into a complete 
       forensic package. Developers can see exactly what the client 
       was doing before the event occurred.
     • **Asynchronous by default**: The queue‑based design means the 
       client never waits for a database write, making the system 
       resilient under high load.
     • **Ethical by construction**: IP addresses are hashed before 
       storage, and the only user data stored is what is explicitly 
       provided in the user object. No hidden tracking.

2. EventLogger.batchEvents(eventsArray)
   ────────────────────────────────────────────────────────────────
   **Purpose**: Record multiple events in a single call, reducing 
   network overhead and enabling atomic group writes.

   **Signature**:
     batchEvents(events: Array<EventSpec>)

   **Behaviour**:
     1. **Iterative Enrichment** – For each event in the array, the 
        same validation and enrichment pipeline as `newEvent` is 
        applied. If any event fails validation, the method collects 
        all failures but continues processing the others.
     2. **Grouping & Ordering** – Events are grouped by user to 
        maintain consistency (e.g., session‑start and subsequent 
        events from the same user are written in order). Within a 
        group, the original order from the array is preserved.
     3. **Bulk Insert** – After enrichment, all events are inserted 
        using a single multi‑row SQL `INSERT` statement. This is 
        significantly faster than individual inserts and reduces 
        database load.
     4. **Return Summary** – The method returns an object:
        ```
        {
          succeeded: number,
          failed: Array<{ index: number, error: string }>
        }
        ```
        This allows the client to retry failed events if needed.
     5. **Client Logs in Batches** – Each event still carries its own 
        `clientLogs` object. No aggregation is performed across events.

   **Strengths & Innovative Nature**:
     • **Optimized for high‑volume clients**: Mobile apps that generate 
       many events per session can send them in batches, reducing 
       battery drain and network usage.
     • **Transactional safety**: While the batch is not wrapped in a 
       database transaction (to avoid locks), the bulk insert ensures 
       that either the entire batch is written or none is. Failures 
       are reported per event, giving the client fine‑grained control 
       over retries.
     • **Preserves context**: Because each event carries its own user 
       and client logs, batching does not lose the ability to debug 
       individual interactions.

3. EventLogger.getEvents(query)
   ────────────────────────────────────────────────────────────────
   **Purpose**: Query the event stream for analytics, debugging, and 
   AI consumption.

   **Signature**:
     getEvents({
       userId?: string,
       sessionId?: string,           // extracted from details JSON
       eventName?: string,
       fromDate?: string,            // ISO timestamp or client date
       toDate?: string,
       limit?: number,               // default 1000, max 10000
       offset?: number,
       includeClientLogs?: boolean,  // default false (for performance)
       sortOrder?: "asc" | "desc"    // default "desc"
     })

   **Behaviour**:
     1. **Build SQL Query** – The method constructs a parameterized 
        `SELECT` query against the `events` table. Indexes are used 
        on `user_id`, `event_name`, and `server_timestamp`.
     2. **Session ID Handling** – Since `sessionId` is stored inside 
        the `details` JSON column, the query uses a JSON path 
        expression (e.g., `details->>'$.sessionId'`) to filter. 
        This is indexed with a generated column if needed.
     3. **Client Logs Exclusion** – By default, `includeClientLogs` 
        is `false` because the `client_logs` JSON can be large. 
        The dashboard or analytics engine can request them explicitly.
     4. **Result Format** – Returns an array of event objects with 
        the same structure as stored (including `id`, `user_id`, 
        `event_name`, `details`, `client_logs` if requested, etc.).

   **Strengths & Innovative Nature**:
     • **Unified query interface**: All data lives in one table, so 
       cross‑event queries (e.g., “users who added a blue thobe and 
       then abandoned checkout”) are simple SQL joins on the same 
       table.
     • **Optimized for analytics**: The query method is designed to 
       be used by the admin dashboard’s graphing engine as well as 
       the AI insight generator. It supports pagination and filtering 
       without exposing the underlying schema.
     • **Session‑aware**: Because `sessionId` is stored in the 
       `details` JSON, the method can treat sessions as first‑class 
       citizens without needing a separate table. This is a direct 
       consequence of the monolithic event design.

4. (Internal) Schema Management
   ────────────────────────────────────────────────────────────────
   Although not a public method, the `EventLogger` contains internal 
   logic for retrieving and caching event schemas from the 
   `event_schemas` table. This table is populated once during 
   deployment (via migration scripts) and is rarely updated. The 
   internal method `_getSchema(eventName)` queries the table, caches 
   the result in memory, and uses it for validation. If a schema is 
   not found, the event is rejected unless a configuration flag 
   allows “unregistered” events to be stored with a warning. This 
   design eliminates any need for a `registerEventType` method or 
   startup calibration; the system is fully data‑driven.


DATABASE SCHEMA
────────────────────────────────────────────────────────────────

**Table: events**
| Column            | Type          | Description                                 |
|-------------------|---------------|---------------------------------------------|
| id                | BIGINT        | Auto‑increment primary key                  |
| event_id          | UUID          | Unique identifier for the event             |
| user_id           | VARCHAR(255)  | Hashed or raw user ID (from auth)           |
| auth_token_hash   | VARCHAR(255)  | Hash of the auth token (for debugging)      |
| event_name        | VARCHAR(255)  | e.g. "add-to-cart", "screen-view"           |
| details           | JSONB         | Polymorphic event details                   |
| client_logs       | JSONB         | Last 10 client logs (appended by client)    |
| hashed_ip         | VARCHAR(64)   | SHA‑256 of client IP                        |
| device_info       | JSONB         | OS version, device model, etc.              |
| server_timestamp  | TIMESTAMPTZ   | When the event was received by the server   |
| client_timestamp  | TIMESTAMPTZ   | Client‑provided timestamp (from dateTime)   |

**Indexes:**
- `idx_user_id` on `user_id`
- `idx_event_name` on `event_name`
- `idx_server_timestamp` on `server_timestamp`
- `idx_user_event_time` composite on `(user_id, event_name, server_timestamp)`
- Generated column `session_id` extracted from `details` (if needed for faster queries)

**Table: event_schemas**
| Column        | Type          | Description                                 |
|---------------|---------------|---------------------------------------------|
| event_name    | VARCHAR(255)  | Primary key                                 |
| schema_json   | JSONB         | JSON Schema definition for `details`        |
| options_json  | JSONB         | Metadata (milestone flag, funnel flag, etc.)|


CLIENT LOGS AUTOMATIC INCLUSION
────────────────────────────────────────────────────────────────

The client (Android/iOS) maintains a circular buffer of the last 10 
client‑side log entries. Each entry is a structured object containing:
- `timestamp`: client‑side timestamp (ISO string)
- `type`: e.g., "screen_view", "network_request", "error", "user_action"
- `message`: a short description
- `data`: optional additional context (e.g., network response code, 
  screen name, error stack)

When the client sends an event to the server (via `newEvent` or 
`batchEvents`), it automatically appends the current buffer as the 
`clientLogs` field. This field is a JSON array of the last 10 entries, 
preserving order (most recent last). The client does not need to 
manage this separately; it is part of the base event‑sending logic.

This approach ensures that every server‑side event is accompanied by 
a replay of the user’s recent client‑side experience, dramatically 
simplifying debugging. For example, if a `checkout-error` event 
appears, the client logs will show the last few screens viewed and 
any network failures that preceded it.


COMPLIMENTARY CLIENT CLASS (Android / iOS)
────────────────────────────────────────────────────────────────

To support the server‑side `EventLogger`, a client‑side utility class 
is provided for native Android (Kotlin) and iOS (Swift) applications. 
This class has two primary public methods:

1. **ClientLogger.append(logEntry)**
   – Internal method that adds a structured log entry to the circular 
     buffer. It is automatically called by the app’s core components 
     (e.g., screen change listeners, network interceptors, error 
     handlers). Developers can also manually call it for custom events.
   – The buffer is maintained in memory; when the app is backgrounded 
     or killed, the buffer is lost (by design – no persistence to disk 
     to respect privacy).

2. **ClientLogger.sendEvent(eventName, details)**
   – The main method used by application code to record an event.
   – It accepts `eventName` and a `details` object (map/dictionary).
   – It automatically attaches:
        * The user object (from the app’s authentication state).
        * The current dateTime.
        * The auth token (if available).
        * The current `clientLogs` buffer (last 10 entries) as a JSON‑ 
          serializable array.
   – It then calls the server’s `EventLogger.newEvent` (or 
     `batchEvents` if multiple events are queued) via the network layer.
   – It handles retries (with exponential backoff) for transient 
     network failures, ensuring events are not lost.
   – Optionally, it can buffer events locally (using SQLite or 
     Room/Realm) when offline and flush them when connectivity is 
     restored.

The client class is intentionally simple, with only these two 
methods exposed. It encapsulates all the complexity of log buffering, 
user context, authentication, and network communication, allowing 
application developers to add event logging with a single line of code.


10 ADDITIONAL IDEAS FOR SALES OPTIMIZATION & SYSTEM EXTENSION
────────────────────────────────────────────────────────────────

1. **Automated Funnel Construction** – Because every milestone event 
   is stored with a session ID in its `details`, the analytics 
   dashboard can automatically infer common user journeys using 
   sequence mining. The AIInsightGenerator can then propose new 
   funnels (e.g., “users who view a product → add to cart → customize 
   → purchase”) without manual definition.

2. **Real‑time Alerting on Event Anomalies** – A background worker 
   watches the event stream for sudden drops in critical events (e.g., 
   `checkout-started`). When an anomaly is detected, it triggers a 
   Slack or email alert, enabling rapid incident response.

3. **Session Replay with Client Logs** – The admin dashboard can 
   reconstruct a user’s session by querying all events for that 
   session ID and interleaving the `clientLogs` from each event into 
   a single timeline. This provides a pixel‑perfect replay of the 
   user’s experience, including network calls and errors.

4. **LLM‑Powered Support Ticket Summaries** – When a support ticket 
   is created, the system fetches the last 20 events for that user, 
   extracts the `clientLogs` and event details, and uses an LLM to 
   generate a concise summary (“User attempted to add blue thobe with 
   custom sleeve length; encountered validation error three times; 
   abandoned cart”). This summary is shown to the support agent, 
   cutting resolution time.

5. **Predictive Abandonment Model** – Train a classifier on sequences 
   of events (e.g., `view-product` → `add-to-cart` → `customize` → 
   `abandon`) to identify high‑risk carts in real time. The system can 
   then trigger a push notification with a limited‑time discount.

6. **Dynamic Marketing Campaigns** – Use the unified event stream to 
   segment users by their recent milestone events. For example, users 
   who completed the welcome quiz but have not made a purchase in 7 
   days receive a targeted email with a curated collection. Campaigns 
   can be defined and launched directly from the dashboard.

7. **Geographic Trend Heatmaps** – Since each event includes a hashed 
   IP, the system can aggregate events by approximate geographic 
   region (via IP geolocation) and display heatmaps of customisation 
   choices (e.g., “royal blue thobes are trending in the Middle East, 
   charcoal grey in Europe”). This informs inventory and marketing 
   decisions.

8. **A/B Test Assignment as Events** – Register an event type 
   `experiment-assignment` with details containing test name and 
   variant. The AIInsightGenerator can then correlate this event 
   with downstream conversion events to automatically rank variants 
   and suggest winners.

9. **Funnel Health Dashboard** – A visual interface that shows the 
   conversion rates for every defined funnel, colour‑coded by 
   performance against historical averages. Clicking on a funnel 
   shows the exact event‑level breakdown, with the ability to filter 
   by device type, user segment, or date range.

10. **Privacy‑Compliant Data Export API** – Extend `getEvents` to 
    allow a user to request all their data in a human‑readable format. 
    The system would query all events for that user, sanitise the 
    client logs (removing any potentially sensitive internal 
    information), and return a JSON or CSV file, fulfilling GDPR/CCPA 
    requirements with minimal development effort.
